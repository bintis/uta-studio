# Uta! Studio UI 恢复、API 覆盖与实机验证计划

> 本计划的功能实现阶段已完成；当前功能与模型状态见 [`../tasks/remaining-models/STATE.md`](../tasks/remaining-models/STATE.md)，最终仓库、Nix 产物和实机发布验收以 [`engineering-constraints.md`](engineering-constraints.md) 的发布检查为准。

## 背景

项目经过一次重构后虽然可以运行，但部分 UI 功能缺失或不可达。本计划以现有代码、数据结构、命令接口和导出能力为依据，恢复完整功能，并建立可自动测试的本地进程内 API。

软件目前处于测试阶段，不要求保持旧版内部实现或数据接口兼容；如有必要，可以直接重构。但必须保护用户源媒体、模型，破坏性测试前记得备份。
磁盘容量不够时候直接ngc命令

## 测试环境

- 操作系统：NixOS
- 桌面环境：COSMIC（Wayland）
- 目标显示器：DP7 副屏
- 尺寸：24.3 英寸
- 分辨率：1920 × 1080
- 刷新率：240 Hz
- 只使用 Wayland，不启用 X11 或 XWayland fallback

实机测试前应记录显示器连接器、缩放比例、窗口尺寸和实际刷新状态，以便复现测试结果。

## 一、功能盘点与 UI 恢复

1. 根据现有 Rust、前端、Python、数据结构、命令注册、导出器和测试代码，反推产品应具备的 UI 功能。
2. 建立功能盘点表，每项至少记录：
   - 功能名称与用户入口
   - 对应页面或组件
   - 后端能力和数据来源
   - 本地 IPC API
   - 当前状态
   - 正常路径、错误路径和测试状态
3. 将功能分类为：
   - 已实现且可用
   - 后端存在但 UI 缺失
   - UI 存在但 API 缺失
   - 功能存在但已损坏或不可达
   - 尚未实现
4. 恢复缺失功能时遵循 Uta! Studio 的现有产品与交互规范，不机械复制其他产品。
5. 歌曲选择进入独立页面；设置仅通过左侧导航进入；chart inspector 默认关闭；歌词可隐藏以扩展时间轴和频谱区域。
6. 文件夹必须支持多个根目录、浏览和授权的上下文菜单操作；歌曲和文件菜单应提供适用的编辑、打开及定位操作。

## 二、本地 API 与代码质量

1. 每个应用自有功能必须具备对应的本地进程内命令 API，或在能力注册表中有明确表示。
2. 不新增未认证的 HTTP 控制服务器。
3. 每个 API 必须分类为：
   - `read`
   - `mutation`
   - `destructive`
   - `external`
   - `temporary`
4. 保持 `api_capabilities` 与原生桌面端实际暴露的操作同步。
5. API 使用结构化请求、返回值和可测试的错误信息；UI 必须处理 API 的失败、超时或能力缺失状态。
6. `run_feature_diagnostics` 必须对用户数据安全：
   - 仅可在唯一临时目录中生成并验证测试导出
   - 完成后删除临时目录
   - 不得删除缓存、断开媒体库、安装模型、保存 chart、触发重新分析或执行其他修改性流程
7. 避免巨大函数，按清晰的模块边界拆分代码。
8. 任一应用源码文件不得超过 2000 行；超过时必须先拆分或重构。

## 三、用户数据与运行时安全

1. 可以使用实际程序文件夹中的媒体、模型和数据进行只读验证。
2. 所有 mutation、destructive 和导出测试必须使用隔离 fixture、数据库副本或唯一临时目录。
3. 不得移动、删除、覆盖或修改用户源音频。
4. 不得删除、替换或重新下载已有模型目录。
5. 程序启动、页面渲染和诊断运行不得自动下载工具、Python 包或 AI 模型。
6. 模型与 runtime 安装必须由用户在 **Settings > Models & runtime** 中显式操作并确认。
7. 导出不得静默覆盖已有文件，必须校验目标扩展名、原子写入，并在失败时清理临时输出。
8. 无损音频使用 FLAC，有损音频使用 MP3；扩展名、编码内容和 MIME 类型必须一致。

## 四、逐功能验收标准

每项 UI 功能至少验证：

1. 正常操作路径
2. 空数据状态
3. 加载状态
4. 禁用或依赖缺失状态
5. 错误路径及可理解的 UI 提示
6. 鼠标、键盘和焦点状态
7. IPC 成功与失败返回
8. 需要持久化的状态在重启后正确恢复
9. 1920 × 1080 目标屏幕及较窄窗口下的布局
10. 自动化测试和 DP7 实机测试结果

模型/runtime 不可用时，分析控件必须禁用，并明确提示用户前往 **Settings > Models & runtime** 完成设置。

## 五、编辑器和音频专项验证

1. 验证播放、暂停、停止、跳转，以及跳转后原播放/暂停意图保持不变。
2. 原生音频位置是时钟源；播放头在轻量状态同步之间通过动画帧平滑插值。
3. 编辑器通过本地进程内命令边界试听所选源文件，Linux 使用原生 GStreamer 播放。
4. 使用真实 chart 连续试听，确认 PipeWire stream 处于运行且未静音，并检查 quantum error 和 xrun；不能只以 stream 存在作为播放成功依据。
5. 验证 waveform/timeline 渲染不会阻塞播放；避免在高并行构建占满系统时判断音频质量。
6. 音符拖动与视口平移必须互不冲突。
7. 时间和音高视口可以独立平移；支持水平与垂直缩放，并可到达当前音符范围之外的音高。
8. 指针交互使用 pointer capture，并在全局 release/cancel 时正确清理。
9. 用户手动滚动后，暂时停止播放头自动跟随。
10. 无重叠音符引导的歌词必须有清晰标记但仍可编辑。
11. 重叠或很短的歌词区间使用无碰撞视觉轨道；较长控件应换行而非覆盖相邻内容。
12. Space 在非可编辑控件聚焦时每次按键仅切换一次播放状态。

## 六、导出验证

1. UTZ 与 UltraStar 均为一等导出格式，涉及 chart authoring 的改动必须覆盖两者。
2. 对两种格式执行真实 smoke export，并验证导出内容而非仅检查文件存在。
3. 验证目标扩展名、非覆盖行为、原子写入和失败清理。
4. 执行真实音频解码测试，确认实际编码与声明格式一致。

## 七、DAG 图优化

1. 在 DP7 上截取改动前后的截图并纳入报告。
2. 优化布局、间距、层级、连线、配色和状态表达，使其符合 Uta! Studio 的视觉方向。
3. 节点的默认、选中、运行中、成功、失败和禁用状态必须容易区分但不过度醒目。
4. 长名称不得溢出；大图应支持缩放、平移和适配视口。
5. 测试空图、单节点、线性流程、多分支、失败节点和大规模图。
6. 保证文本对比度、焦点可见性和键盘操作，不以美化为理由降低可访问性。

## 八、DP7 实机与 IPC 测试

1. 在 DP7（24.3 英寸、1920 × 1080、240 Hz）副屏上启动程序。
2. 通过本地 IPC 逐项测试能力注册表中的功能。
3. 同时执行 UI 操作，确认 API 行为、界面状态和持久化结果一致。
4. 记录每项功能的通过、失败、阻塞或不适用状态，并附错误信息和必要截图。
5. 对 mutation API 使用隔离测试数据；禁止通过真实用户库证明 destructive API 可用。
6. 检查高刷新率下的动画、滚动、播放头和 DAG 交互是否平滑，同时确认 CPU/GPU 占用无明显异常。

## 九、完成前检查

完成前至少执行并记录：

- Rust formatting、check 和 tests
- Python compile checks
- 原生 UI tests 与 build
- API registry contract test
- 真实音频 decode
- 真实 UTZ smoke export
- 真实 UltraStar smoke export
- 应用源码文件 2000 行限制检查
- 不允许的旧项目名称扫描
- `nix build path:.#uta-studio`
- 从 Nix 构建产物的 wrapped executable 启动并完成 smoke test

## 十、工作报告

全部工作完成后提交报告，至少包含：

- 功能盘点与最终状态表
- 恢复或新增的 UI 功能
- 新增、修改和移除的 API
- API 分类及 `api_capabilities` 同步情况
- 主要重构及文件拆分说明
- DAG 改动前后截图
- 自动化测试结果
- DP7 实机测试环境与逐项结果
- 音频播放、真实解码和导出验证结果
- Nix 构建产物路径及 smoke launch 结果
- 未完成项、已知问题和风险
- 用户数据安全说明

## 完成定义

只有当一项功能具备可达且可用的 UI、对应的本地 IPC、正常与错误路径测试、DP7 实机验证，并且相关构建及 smoke test 通过后，才可标记为完成。
